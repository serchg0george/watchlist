# watchlist — Project Instructions

Трекер фильмов, сериалов и шоу на GitHub Pages: список «посмотреть», отметка просмотренного, оценка от 0,5 до 10 с шагом 0,5, статистика. Данные — `data/movies.json` в этом репозитории; сайт пишет их через GitHub API токеном пользователя. Редактировать могут только владелец и один коллаборатор (права на запись в репо).

> **Codex:** read `CODEX.md` first; it overrides this file where they differ.

## 1. Git & GitHub

GitHub user **serchg0george**, repo **serchg0george/watchlist**, branch **master**. GitHub Pages собирается workflow `deploy.yml` после зелёного CI в `master` и при rollover: код из `master`, `data/movies.json` из текущей ветки `data/*`; правки данных с сайта деплой не запускают.

- Перед работой: `gh auth switch --user serchg0george` (не `gh auth status` — зависает), затем `git fetch --all --prune && git pull --ff-only`. Pull не прошёл (diverged, конфликты, auth/network) → стоп, сообщить, спросить. Никаких `rebase`, `merge`, `reset --hard`, force без явного запроса.
- **Identity — MANDATORY.** Перед любым коммитом: `git config --local user.name` = `serchg0george`, `user.email` = `serchg0george@users.noreply.github.com`; если не так — выставить с `--local`. Никогда `git config --global` — глобальный конфиг принадлежит рабочему аккаунту Expedia.
- **Co-authors — MANDATORY.** Каждая модель, работавшая над коммитом, указывается как `Co-authored-by`. `scripts/delegate.sh` регистрирует исполнителя сам; агент сессии добавляет себя перед коммитом: `scripts/coauthor.sh add <alias>` (`scripts/coauthor.sh aliases`). Трейлеры пишет хук `.githooks/prepare-commit-msg`; после клона один раз: `git config --local core.hooksPath .githooks`.
- **Post-push cleanup — MANDATORY.** После push: если `gh auth status` показывает `szavada_expedia`, выполнить `gh auth switch --user szavada_expedia`. Нет такого аккаунта (личная машина) — пропустить.
- `data/movies.json` правится и с сайта (коммиты от имени пользователей). Перед своими изменениями всегда `git pull --ff-only`.
- **Ветки и PR — MANDATORY.** Код в `master` напрямую не коммитится. Один план = одна ветка = один PR со всеми задачами плана (это и есть «патч»); отдельные ветки и PR на задачу или пачку не заводятся. Имена по версии: `patch_1.0.0`, `patch_1.0.1` … `patch_1.0.9`, затем `patch_2.0.0` … `patch_2.0.9` и т.д.; следующий номер — по последней ветке `patch_*` в `git ls-remote --heads origin`. Имя выбирается до первого коммита: переименование ветки на GitHub закрывает её PR.
- **Описание PR патча — MANDATORY.** Детальный список всего, что сделано в патче: каждый пункт — одно предложение по-русски в прошедшем времени («Произведён рефакторинг фронтенда с чистого TS на React», «Введён нейминг веток `patch_X.Y.Z`»). Отдельной строкой — что проверено и что нет. Описание обновляется при каждом push в ветку.
- Коммит — только по явной просьбе («закоммить», «commit»); написанный файл ≠ коммит. Push — только если пользователь сказал «push»/«запушь»; без этого — локальный коммит и стоп. «Uncommitted» — оставить в рабочем дереве.
- Хук `.githooks/post-commit` очищает список соавторов после первого коммита: при нескольких коммитах подряд трейлеры `Co-authored-by` передавать явно (`git commit --trailer ...`).

## 2. Language & Style

- Коммиты — **English**. Интерфейс сайта, документация, общение — **Russian**. Задачи и промпты для других моделей (`delegate.sh`, сабагенты) — **English**, UI-строки внутри них — русские.
- Ответ пользователю — не длиннее 155 символов (код, вызовы инструментов, диффы не считаются). Вопрос да/нет — ответ начинается с «Да.» или «Нет.» и максимум одно короткое пояснение.
- Без приветствий, пересказа вопроса, комментариев к своим действиям («сейчас посмотрю…»), итоговых списков «что сделал», непрошенных следующих шагов, извинений; без заголовков и списков в коротких ответах. После задачи — одна строка с результатом, детали по запросу.
- Длиннее можно только: по явной просьбе о деталях; при анализе (разбор кода, причина бага, сравнение вариантов); при написании документа (README, план, спека, описание PR); при код-ревью; при блокере, который пользователь не решит без деталей. Даже тогда — плотно, без воды.
- Строго и по делу, без нравоучений. Не ссылаться на номера и названия правил в ответах, не пересказывать процедуры, без чек-листов выполненных шагов. Меньше слов по умолчанию.
- Всё, что пользователь должен куда-то вставить, — полный финальный текст в одном блоке кода.

## 3. Структура

- Сайт — React 19 + Vite + строгий TypeScript. `index.html` — только `<div id="root">` и вход `src/main.tsx`; статика (`style.css`, `manifest.json`, `icons/`) — в `public/`, Vite копирует её в `dist/` без переименования. `src/`: `config.ts` (константы), `domain/` (чистая логика без DOM: типы, normalize, ops — изменения данных как сериализуемые `Op`, `applyOp`, validate, stats), `data/` (`GitHubRepository` за `WatchlistRepository`, `SaveQueue`), `state/` (`store.ts` — состояние, `render()` и подписка для React, `saving.ts`, `toast.ts`), `actions.ts` (действия пользователя), `ui/react/` — компоненты (`App`, `Header`, `ListTab`, `ItemRow`, `Stars`, `Comments`, `Editor`, `BulkBar`, `Stats`, `SettingsDialog`, `CategoriesDialog`, `Toast`), `tmdb.ts` (поиск TMDB; сам наполняет форму добавления по id), `main.tsx` (init и монтирование `App`). `domain/`, `data/`, `state/`, `tmdb.ts`, `config.ts`, `util/` React не импортируют. Состояние мутируется на месте, `render()` уведомляет React (`useWatchlist()`).
- `npm run dev` — локальный сервер Vite; `npm run build` — `tsc -p tsconfig.sw.json` (сервис-воркер в `.sw-build/`) и `vite build` в `dist/`; `dist/`, `.sw-build/` в `.gitignore`, `deploy.yml` публикует `dist/` и `data/movies.json`. Зависимости: `react`, `react-dom`; dev — `vite`, `@vitejs/plugin-react`, `typescript`, типы React, `vitest`, `@testing-library/react`, `jsdom`. Перед коммитом — `npm run check && npm test` (`node --test` для домена и `vitest run` для компонентов в `tests/react/`).
- `public/manifest.json`, `src/sw.ts`, `public/icons/` — установка на телефон и офлайн-кэш (network-first). `SHELL` в `sw.ts` — заглушка: при сборке плагин в `vite.config.ts` подставляет все файлы `dist/` (`tools/sw-shell.ts`, проверяет `tests/sw-shell.test.ts`). Вручную список не ведётся; при изменении логики кэша поднять `CACHE` в `src/sw.ts`.
- `data/movies.json` — данные (схема в `README.md`); `npm run validate-data` их проверяет, Weekly rollover не пушит невалидные данные, Deploy Pages публикует сайт, но краснеет.
- `scripts/` — `delegate.sh`, `qwen.sh`, `coauthor.sh`. `.githooks/` — трейлеры соавторов.

## 4. Local Qwen Lifecycle — MANDATORY

Локальная модель — Qwen3.8-27B в LM Studio (`qwen-local`). Управление: `scripts/qwen.sh up | down | status`. `up` — перед делегированной работой (`scripts/delegate.sh` поднимает сам); `down` — сразу после успешного push. Никогда не оставлять загруженной между сессиями.

## 5. Delegated Work — MANDATORY

Агент сессии (любой: Claude, Codex и т.п.) решает, локальная модель печатает. Основная работа — код сайта, README, правки данных, переносы текста — идёт через `scripts/delegate.sh <task-file>` (по умолчанию локальная Qwen; `--acli` — Antigravity Flash Low, если локальная модель недоступна). Скрипт работает в одноразовом клоне без remote и возвращает патч; агент пишет задачу, проверяет патч, применяет `git apply`, исправляет, коммитит и пушит. Порядок работы по плану (подзадачи, исполнитель и уровень ревью на каждую, поверхностный гейт, финальное ревью) — навык `delegate-plan` из `serchg0george/agent-skills`.

- Агент делает анализ, решения, текст задачи, ревью и финальные правки после ревью.
- Неверный патч → одна повторная попытка с исправленной задачей, затем агент правит сам.
- Две большие локальные модели одновременно в память не помещаются: перед сменой модели `scripts/qwen.sh down`. Параллельно — только локальная + `--acli`, если файлы задач не пересекаются; `--acli` в headless-режиме не запускает команды, поэтому в его задачах нет шагов «запусти тесты» — их прогоняет агент.
- Правка короче текста задачи (опечатка, одна строка) делается напрямую.
- Локальной модели отдаются крупные однотипные правки; точечные UI-фиксы и правки в несколько строк агент делает сам — цикл «задача → патч → ревью» не должен быть дольше самой правки.
- Исключение — только по явной просьбе пользователя о скорости или переносимости (сессия с телефона и т.п.); тогда агент правит напрямую.
